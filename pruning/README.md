# Структурный прунинг SegFormer-B0 (torch_pruning)

Учебная часть проекта: как устроены зависимости между слоями трансформера и что из них можно
удалять. Исходная модель — итоговая SegFormer-B0 из `../weights/segformer-b0-camvid`
(вход 360×480, test mIoU 0.691).

## Шаг 1. Граф зависимостей

```bash
python3 pruning/dependency_groups.py      # -> pruning/results/dependency_groups.md
python3 pruning/plot_dependency_graph.py  # -> pruning/results/dependency_graph.html
```

`dependency_graph.html` — интерактивный граф из того же DepGraph, открывается в браузере.
Режим «layers only» показывает связи слой → слой, «full graph» — все 465 узлов, включая
операции без весов (`reshape`, `transpose`, `add`, `SDPA`, `cat`), через которые DepGraph
протягивает зависимости. Цвет слоя — группа его выходных каналов; при наведении видны
размерности и группы по входу и выходу.

### Что такое группа зависимостей

Структурный прунинг удаляет не отдельные веса, а целые каналы: строку выходных весов одного
слоя. Но этот канал читают следующие слои, поэтому их входные веса тоже нужно уменьшить, иначе
не сойдутся размеры. `torch_pruning` прогоняет модель на примере входа, строит граф операций
(DepGraph) и для каждого канала находит **группу** — все слои, которые нужно изменить вместе.
В графе он проходит и через операции без весов: `view`, `transpose`, сложения residual, SDPA.

HF-модель возвращает не тензор, а объект, поэтому граф строится так:

```python
tp.DependencyGraph().build_dependency(
    model, example_inputs={"pixel_values": x}, output_transform=lambda out: out.logits)
```

### Какие группы есть в SegFormer-B0

31 группа пяти типов (классификатор не трогаем — его выход это 11 классов):

| Тип | Групп | Каналов | Слоёв в группе | Что связано |
|---|---|---|---|---|
| Mix-FFN hidden | 8 (по одной на блок) | 128 / 256 / 640 / 1024 | 3 | выход `fc1` → depthwise-свёртка → вход `fc2` |
| attention Q/K/V → O | 8 | 32 / 64 / 160 / 256 | 4 | выходы `q_proj`, `k_proj`, `v_proj` → вход `o_proj` |
| key/value reduction | 6 (нет в stage4, там R = 1) | = C | 4 | свёртка сжатия + её LayerNorm → входы `k_proj`, `v_proj` |
| residual stream C | 4 (по одной на стадию) | 32 / 64 / 160 / 256 | 19–20 | вся стадия: patch embedding, все LayerNorm, входы Q и сжатия, выходы O и `fc2`, вход следующей стадии и `linear_c` декодера |
| decoder | 5 | 256 | 2–3 | `linear_c_i` → вход `linear_fuse`; `linear_fuse` → BatchNorm → вход классификатора |

Что из этого следует:
- **Mix-FFN — самый «дешёвый» кандидат.** Каждый блок — своя группа из 3 слоёв; канал скрытого
  слоя ни с чем вне блока не связан. Depthwise-свёртка (`groups` = числу каналов) своей ширины
  не имеет и режется вместе с `fc1`.
- **Residual-поток — самый дорогой.** Один канал C тянет за собой 19–20 слоёв всей стадии, включая
  вход следующей стадии и декодера: residual-сложения требуют одинаковой ширины во всех блоках.
- **Сжатие ключей — отдельная группа.** Свёртка `sequence_reduction` выдаёт свою копию C только для
  K и V, поэтому её выход можно сужать независимо от residual-потока. Q при этом читает несжатый
  residual-поток.
- **Декодер.** Четыре проекции `linear_c` склеиваются (`cat`) на входе `linear_fuse`, поэтому
  каждую можно сузить отдельно; выход `linear_fuse` (ширина декодера) связан только с BatchNorm и
  классификатором.

### Ловушка: головы внимания

DepGraph связывает Q, K, V и O поканально, но **не знает про головы**. В SegFormer
`head_dim` = 32 зашит в модуль, а число голов вычисляется в `view(..., -1, 32)` из ширины тензора.
Опыт на `stage2.blocks.0.attention` (2 головы × 32 = 64 канала):

| Удалили | Результат |
|---|---|
| 1 канал | падение: 63 канала не делятся на 32 |
| 32 канала с 10-го по 41-й | работает, но молча неправильно: остатки двух голов склеились в одну «голову» с перемешанными каналами |
| 32 канала 32…63 = голова 1 целиком | работает, структура внимания сохранена |

Разница выходов (2.3 против 6.1) тут ничего не говорит о правильности: удаление целой головы
просто убирает больше информации, и после него нужно дообучение. Но только этот вариант
сохраняет смысл механизма внимания. Отсюда правило: **в attention удаляем только целые головы**
(в `torch_pruning` — `num_heads={...}` и `prune_num_heads=True`), а в stage1 голова одна —
её не трогаем.

### Что можно убрать: граф + код + цена

Граф показывает, какие слои меняются вместе, но не знает, какие размеры зашиты в коде модели.
Поэтому каждую группу проверили удалением одного канала (для внимания — одной головы) и
прогоном модели; цена — сколько параметров и MACs уходит за этот канал.

| Группа | Слоёв | Работает после прунинга? | Минус за 1 канал (голову) |
|---|---|---|---|
| Mix-FFN, stage1 (128 каналов) | 3 | да | 75 параметров, 0.80 MMACs |
| Mix-FFN, stage3 (640) | 3 | да | 331 параметр, 0.23 MMACs |
| Mix-FFN, stage4 (1024) | 3 | да | 523 параметра, 0.09 MMACs |
| голова внимания, stage2 (1 из 2) | 4 | да, если целиком | 8 288 параметров, 11.7 MMACs |
| голова внимания, stage4 (1 из 8) | 4 | да, если целиком | 32 864 параметра, 5.9 MMACs |
| сжатие K/V (stage1–3) | 4 | **нет** | — |
| residual C, stage1–3 | 19 | **нет** | — |
| residual C, stage4 | 20 | да | 7 857 параметров, 1.4 MMACs |
| декодер, `linear_c_i` | 2 | да | 289 параметров, 3.1 MMACs |
| декодер, ширина (`linear_fuse`) | 3 | да | 1 037 параметров, **11.2 MMACs** |

**Почему сжатие K/V и residual в stage1–3 не режутся.** В `SegformerSequenceReduction` после
свёртки тензор переформатируется с *входным* числом каналов:

```python
batch_size, seq_len, num_channels = hidden_states.shape
hidden_states = self.sequence_reduction(hidden_states)              # Conv2d(C, C, R, stride=R)
hidden_states = hidden_states.reshape(batch_size, num_channels, -1)  # ждёт C на выходе свёртки
```

То есть код требует, чтобы выход свёртки сжатия был равен C. DepGraph видит только поток данных и
считает эти размерности независимыми: сужение выхода свёртки или residual-потока в стадии со
сжатием ломает этот `reshape`. В stage4 сжатия нет (R = 1), там residual режется. Обойти можно,
переписав `forward` модуля (брать число каналов из выхода свёртки) или сужая residual и выход
сжатия одновременно, — но это уже правка архитектуры, а не готовый прунинг.

**Как читать цену.** Один и тот же канал стоит по-разному в зависимости от разрешения стадии:
канал Mix-FFN в stage1 почти ничего не весит (75 параметров), но обрабатывается на 10 800 токенах
и даёт 0.80 MMACs; в stage4 наоборот — 523 параметра, но всего 0.09 MMACs на 180 токенах (карта 12×15). Прунинг
ранних стадий уменьшает вычисления, поздних — размер модели. Самый дорогой по вычислениям канал —
ширина декодера: 11.2 MMACs, поскольку `linear_fuse` работает на карте 90×120 с 1024 входами.

**Чего граф не говорит.** Насколько каждый канал важен для качества. Это определяет критерий
важности (норма весов, Тейлор) и в конечном счёте замер mIoU — следующий шаг.

## Шаг 2. Чувствительность групп без дообучения

```bash
python3 pruning/prune_segformer.py --ratios 0.1 0.25 0.5 0.75 --importance l1 random --compile --tag sweep
# -> pruning/results/prune_sweep.md, .json
```

Каждая цель режется отдельно на свежей копии модели (`MetaPruner`, остальные слои в
`ignored_layers`), затем меряются параметры, GMACs, mIoU на val **без дообучения** и задержка
(batch 1, 360×480). Цели: `mlp` — скрытый слой Mix-FFN во всех блоках; `heads` — головы внимания
в stage2–4 целиком (`num_heads`, `prune_num_heads=True`, `prune_head_dims=False`); `decoder` —
`linear_c` и ширина декодера; `residual4` — residual-поток stage4. Критерий важности — L1-норма
весов канала по всей группе (`GroupMagnitudeImportance`), для контроля — случайный выбор.

Исходная модель: 3.717 млн параметров, 4.94 GMACs, mIoU val 0.7734, задержка 7.33 мс (fp32) /
3.38 мс (fp16+compile). Критерий L1:

| Цель | Доля | Форма после | Параметры | GMACs | Δ mIoU val | fp32, мс | fp16+compile, мс |
|---|---|---|---|---|---|---|---|
| mlp | 0.10 | 112/224/576/920 | −4 % | −2 % | −0.040 | 7.19 | 3.34 |
| mlp | 0.25 | 96/192/480/768 | −11 % | −4 % | −0.090 | 6.96 | 3.42 |
| mlp | 0.50 | 64/128/320/512 | −21 % | −9 % | **−0.408** | 6.68 | 3.05 |
| heads | 0.25 | 1/1/3/6 | −6 % | −4 % | −0.021 | 7.10 | 3.38 |
| heads | 0.50 | 1/1/2/4 | −11 % | −5 % | −0.051 | 7.06 | 3.42 |
| decoder | 0.10 | 224 | −2 % | −14 % | −0.002 | 7.01 | 3.25 |
| decoder | 0.25 | 192 | −4 % | −26 % | −0.018 | 6.61 | 3.03 |
| decoder | 0.50 | 128 | −7 % | **−45 %** | **−0.397** | **5.94** | **2.65** |
| decoder | 0.75 | 64 | −9 % | −57 % | −0.576 | 5.34 | 2.29 |
| residual4 | 0.25 | 192 | −14 % | −2 % | −0.020 | 7.26 | 3.43 |
| residual4 | 0.50 | 128 | **−27 %** | −4 % | −0.089 | 7.19 | 3.40 |

Что видно:
- **Время уменьшает только прунинг декодера.** Половина ширины декодера даёт −45 % GMACs и −22 %
  задержки в fp16+compile (3.38 → 2.65 мс). Головы и residual stage4 убирают до 27 % параметров, но
  задержка не меняется: stage4 работает на карте 12×15 и почти ничего не стоит по времени. Это
  ровно то, что показал профиль: время SegFormer — в декодере и операциях с памятью, а не в
  параметрах.
- **Чувствительность групп разная.** Головы и residual stage4 переносят 25–50 % почти без потерь
  (−0.02…−0.09). Mix-FFN и декодер обваливаются уже на 50 % (−0.40): скрытый слой MLP и ширина
  декодера плотно используются, и без дообучения сеть не компенсирует потерю.
- **L1-норма — слабый критерий без дообучения.** Для Mix-FFN на 10 % и 50 % и для декодера на 50 %
  случайный выбор каналов оказался *не хуже* L1 (декодер 0.50: −0.165 у случайного против −0.397 у
  L1). Маленькая норма весов не означает маленький вклад: после LayerNorm и BatchNorm масштаб канала
  восстанавливается. Окончательно качество определит дообучение.
- **Ловушка округления голов.** При доле 0.75 в stage2 должно остаться 0.5 головы, и
  `torch_pruning` не трогает группу вовсе: получается 1/**2**/1/2 вместо 1/1/1/2. Поэтому 0.75 по
  mIoU выглядит лучше 0.5 (−0.030 против −0.051). Форму после прунинга надо проверять по всем
  блокам, а не по доле.

## Шаг 3. Дообучение урезанных моделей

```bash
python3 pruning/finetune_pruned.py none "decoder:0.25" "decoder:0.5" "mlp:0.25" \
    "heads:0.5,residual4:0.25" "decoder:0.5,heads:0.5,residual4:0.25" --epochs 30 --compile --tag finetune
# -> pruning/results/finetune.md, .json; веса -> pruning/outputs/<имя>/ (не в git)
```

Каждый вариант режется из итоговой модели (критерий L1) и дообучается 30 эпох тем же рецептом,
что исходная модель (вход 360×480, scale-crop, CE + Lovász, lr 6e-5 / 6e-4, poly). Берутся веса с
лучшим mIoU на val. `none` — **контроль**: исходная модель без прунинга, дообученная столько же,
чтобы отделить эффект прунинга от эффекта лишних 30 эпох.

Сохраняются `state_dict.pt` и спецификация прунинга (`pruning.json`): чекпоинт урезанной модели
нельзя открыть через `from_pretrained` (в `config.json` исходные размеры), поэтому `load_pruned()`
заново режет исходную модель по спецификации и загружает веса — формы слоёв зависят только от
долей, а не от выбранных каналов.

| Прунинг | Параметры | GMACs | test до дообучения | val (лучший) | **test** | Δ test к контролю | fp16+compile |
|---|---|---|---|---|---|---|---|
| нет (контроль) | 3.717 млн | 4.94 | 0.6912 | 0.7739 | **0.6910** | — | 3.39 мс |
| декодер 0.25 | 3.568 млн | 3.65 | 0.6479 | 0.7691 | 0.6875 | −0.004 | 2.99 мс (−12 %) |
| **декодер 0.5** | 3.453 млн | **2.71 (−45 %)** | 0.2777 | 0.7672 | **0.6906** | **−0.000** | **2.61 мс (−23 %)** |
| Mix-FFN 0.25 | 3.321 млн | 4.72 | 0.6247 | 0.7626 | 0.6803 | −0.011 | 3.23 мс (−5 %) |
| головы 0.5 + residual4 0.25 | **2.877 млн (−23 %)** | 4.62 | 0.5838 | 0.7686 | 0.6850 | −0.006 | 3.33 мс (−2 %) |
| декодер 0.5 + головы 0.5 + residual4 0.25 | **2.621 млн (−30 %)** | **2.40 (−51 %)** | 0.2433 | 0.7630 | 0.6775 | −0.014 | **2.53 мс (−25 %)** |

Задержка — batch 1, 360×480, замер после дообучения в одном процессе. Время fp32 в этом прогоне
шумное (у контроля 8.14 мс против 7.33 мс в остальных замерах), поэтому сравнение по fp16+compile.

Что видно:
- **Контроль ничего не набрал** (0.6912 → 0.6910): 30 лишних эпох исходной модели не помогают,
  значит результаты урезанных моделей отражают именно прунинг.
- **Дообучение восстанавливает почти всё.** Декодер 0.5 до дообучения давал 0.278 на test, после —
  0.691, как исходная модель. Уже после первой эпохи val mIoU 0.74 (исходная 0.77).
- **Лучший вариант — половина ширины декодера**: −45 % GMACs и −23 % задержки без потери mIoU.
  Это главное узкое место по профилю, и оно оказалось избыточным: 128 каналов декодера хватает.
- **Головы и residual stage4 экономят параметры, но не время** (−23 % параметров, −2 % задержки);
  Mix-FFN — самый чувствительный (−0.011 уже на 25 %) при почти нулевом ускорении.
- **Комбинация** даёт максимум: −30 % параметров, −51 % GMACs, −25 % задержки ценой −0.014 mIoU.
- Различия меньше ~0.005 mIoU (декодер 0.25 против 0.5) — в пределах разброса между запусками:
  каждый вариант обучен один раз.
